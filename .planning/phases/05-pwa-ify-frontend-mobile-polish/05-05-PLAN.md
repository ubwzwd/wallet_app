<objective>
Wire the safe-area-inset stack into the app: swap `Screen.tsx`'s SafeAreaView import from `'react-native'` (iOS-only, no-op on web) to `'react-native-safe-area-context'` (cross-platform; web-emits env() insets), and wrap the App.tsx root tree with `SafeAreaProvider`. Per RESEARCH §Anti-Patterns ("Forgetting SafeAreaProvider"), `useSafeAreaInsets()` silently returns zero without the provider, so the wrap is load-bearing. Per CONTEXT D-09, the SW glue MUST be wired here (alongside the provider wrap) to avoid Wave-1 merge conflicts on App.tsx — both edits touch the root tree and pairing them in a single plan eliminates the conflict surface.

Output: Two files modified; `useSafeAreaInsets()` now works on web; App boots with the PWA toast mounted; `verify-touch-targets.mjs` Checks E + F flip GREEN.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05-01 | Tampering / data freshness | Stale-shell trap | mitigate | The SafeAreaProvider wrap + UpdateToast mount complete the user-visible side of the SKIP_WAITING handshake: when 05-03's `subscribeUpdate` fires, the `<UpdateToast />` mounted here is the surface that lets the user opt into the new SW. Without this plan's App.tsx edit, the toast never renders and the user has no escape from a stale shell. |
| T-05-05-02 | Tampering / Spoofing | Service worker hijack | mitigate | SW registers via `navigator.serviceWorker.register('/sw.js')` from the same origin under HTTPS (Caddy from Phase 4); the registration code path in `registerSW.ts` was reviewed in 05-03. |
| T-05-05-03 | Information Disclosure | Cross-user cache leakage | accept | Out of scope for this plan; mitigation deferred per RESEARCH § Security Domain. |
